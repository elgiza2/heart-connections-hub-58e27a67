# تشغيل Knowledge / Cloud Browser / Skills / Integrations / MCP / Custom API بشكل حقيقي

## الوضع الحالي (نتيجة الفحص)

| الميزة | الحالة | المشكلة |
| --- | --- | --- |
| Skills | حقيقية ~80% | تُقرأ من جدول `skills` وتُرسل فعلاً مع كل رسالة. `activeSkill` معطّل، و`enabled_tools` غير مطبّق |
| Integrations / MCP | التخزين حقيقي | البيانات تُحفظ في `mcp_connections` / `user_integrations` لكن **لا تُرسل مع رسالة الشات إطلاقاً** → الموديل لا يعرف بوجودها |
| Knowledge | واجهة فقط | تُحفظ في `user_knowledge` لكن لا أحد يقرأها ولا تُدخل في البرومبت. `siteKnowledge.md` ملف ميت |
| Cloud Browser | ديكور | زر واحد يكتب في localStorage ولا يُقرأ في أي مكان |
| Custom API | اسم تاب فقط | لا يوجد حقل لإدخال مفتاح، والاتصال يرمي خطأ لأي connector غير GitHub/Pipedream/Email |

الشات يعتمد على edge function خارجية `chat-alibaba` غير موجودة في المشروع، فكل التمرير لازم يبدأ من العميل في نفس الـ payload الحالي.

## الخطة

### 1. طبقة سياق موحّدة (الأساس)
ملف جديد `src/lib/chat/turnContext.ts` يجمع قبل كل رسالة:
- سجلات `user_knowledge` المفعّلة (مع حد أقصى للحجم)
- `mcp_connections` المفعّلة → قائمة `mcpServers`
- التكاملات المتصلة (`user_integrations` + `composio_connections`) → `connectedApps`
- حالة Cloud Browser الحقيقية → `browserEnabled`

يُستدعى من `runChatStreamTurn.ts` بجانب `availableSkills` الموجودة، ويُمرَّر في نفس body عبر `streamChat.ts`، وتُضاف نسخة مختصرة نصية إلى `customSystem` حتى يشتغل حتى لو الباك إند تجاهل الحقول الجديدة.

### 2. Knowledge حقيقي
- ربط `user_knowledge` بطبقة السياق مع احترام مفتاح `enabled`.
- بادج في الشات يوضح "Knowledge active" وعدد السجلات المستخدمة.
- حذف `src/data/siteKnowledge.md` أو تحويله إلى معرفة عامة عن الموقع تُحقن في صفحات المساعدة فقط.

### 3. Cloud Browser حقيقي
- جدول `cloud_browser_settings` (المستخدم، keep_signed_in، allow_downloads، الجلسة الأخيرة) بدل localStorage + GRANT + RLS بـ `auth.uid()`.
- الصفحة تقرأ وتكتب من الجدول، والحالة تُمرَّر للشات كقدرة فعلية بدل النص الثابت في `capabilities.ts`.
- قسم "الجلسات النشطة" مع زر تسجيل خروج/مسح الكوكيز.

### 4. Skills إلى نهاية الطريق
- إعادة تشغيل اختيار مهارة صريحة من الكومبوزر (`activeSkill`) بدل `undefined`.
- تمرير `enabled_tools` مع كل مهارة وفرض القائمة على الأدوات المسموحة في العميل.
- عرض المهارة التي اشتغلت داخل الرسالة.

### 5. Integrations + MCP فعّالة
- تمرير السيرفرات والتطبيقات المتصلة في السياق (خطوة 1) حتى يصير الموديل قادر على استخدامها.
- إكمال `integrationBackend.ts`: مسار اتصال عام للـ connectors المتبقية بدل `throw`، ورسالة واضحة لأي مزوّد غير مدعوم فعلاً.
- نقل عمليات MCP من دالة `crawl-url` إلى دالة مخصّصة `mcp-gateway` (فحص السيرفر، جلب قائمة الأدوات، تخزينها) لأن الوضع الحالي هش.
- زر Test في MCP يعرض الأدوات المكتشفة فعلاً ويحفظها.

### 6. Custom API حقيقي (BYOK)
- جدول `user_provider_keys` (user_id، provider، مفتاح مخزّن، آخر تحقق) + RLS صارم، والمفاتيح لا تُقرأ أبداً من العميل بعد الحفظ (كتابة فقط + إظهار آخر 4 خانات).
- صفحة `Settings → Custom API`: إضافة/حذف/اختبار مفتاح لكل مزوّد.
- تاب "Custom API" في شيت التكاملات يفتح هذه الصفحة بدل زر لا يعمل.

### 7. التنظيف والاتساق
- قاعدة ثابتة: لا ظهور لأسماء المزودين أو الموديلات في أي واجهة (نفس ما طُبّق في صفحة Usage) — تُطبّق على MCP وCustom API وSkills.
- تصميم موحّد نظيف لكل الصفحات الجديدة (بدون تدرجات/ظلال ثقيلة).
- فحص الصفحات على الموبايل والديسكتوب بعد كل خطوة.

## ملاحظات تقنية
- كل جدول جديد يأتي مع `GRANT` + `ENABLE ROW LEVEL SECURITY` + سياسات مقيّدة بـ `auth.uid()`.
- المفاتيح السرية لا تُخزّن في كود العميل ولا تُعاد من الـ API.
- الحقول الجديدة في payload الشات إضافية وغير كاسرة، فلو `chat-alibaba` لم تُحدَّث بعد يبقى النص المختصر في system prompt هو المسار الفعّال.
